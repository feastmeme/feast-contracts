**MEDIUM**

**M1 — The fill removes coin between a router’s `sync` and `settle`, invalidating its payment.**

Caller: an ordinary router inside a vault lock. State: an open pool at price 1, mature matching TWAP, sufficient custody, and allowance for a one-token fill. Arguments: an exact-input sale of 1,000 tokens.

The router performs:

1. `vault.sync(coin)`, recording balance `V`.
2. Transfers `X = 1,000e18` coin into the vault.
3. Calls the pool’s swap.
4. Calls `vault.settle()`, then takes its quote proceeds.

The fill passes the custody check, removes and burns `f = 1e18` coin, and returns a delta making the router owe the full sale input `X`. But the vault now holds `V + X − f`; settlement credits only `X − f`. The router retains a negative coin delta of `f`, so lock completion reverts.

The offending transfer is [inside `_fill`](src/FeastHook.sol:490); the local interface documents settlement as the balance increase since [`sync`](src/venue/IFeastVault.sol:19). Without the fill, this sequence settles exactly. This breaks P10 and I1 at ordinary amounts, without a hostile token or insufficient custody.

The existing router always syncs **after** swapping, and the flash-sale witness also syncs after its swap; neither exercises this interval. [Standard router](test/utils/PoolRouter.sol:61), [custody witness](test/FeastInternalFill.t.sol:219)

**Fix and second-order check:** Before effects, decline the optional fill when the vault’s currently synced currency is this coin. The underlying vault exposes that state through `getVaultReserve`. Preserve the router’s snapshot; resetting it would discard its prepayment. Returning no fill preserves the original sale and introduces no new refusal or bucket movement.

**LOW**

**L1 — Negating the minimum signed input rejects a valid, bounded partial sale—even with no burn bucket.**

An exact-input seller can supply `amountSpecified = type(int256).min` and a price limit that bounds actual consumption. The venue handles that negative magnitude in unchecked arithmetic and narrows the **realised** deltas.

Package 1 instead evaluates checked unary negation before entering `_fill`, so it panics before the empty-bucket or other no-fill checks. [New argument conversion](src/FeastHook.sol:404)

A concrete bounded construction is coin as currency0, liquidity `1e20`, starting square-root price `2^96`, and limit `floor(0.999 × 2^96)`. Integer reconstruction using the configured LP fee gives approximately `1.0011e17` coin spent and `9.9e16` quote received after the hook fee—both comfortably within signed 128-bit settlement. The enormous request does not require an enormous realised trade.

The admission fuzz takes only `uint96` input and bounds it further, so it cannot reach this failure. [Fuzz domain](test/FeastInternalFill.t.sol:337)

**Fix and second-order check:** Return no fill for this unsupported magnitude before negation, leaving the original request and venue price limit intact. That restores the otherwise valid sale without changing fee accounting or settlement caps.

**L2 — Intermediate rounding can pay less than both rounded spot and the unfilled sale.**

`_quoteForCoin` floors after each square-root multiplication. That differs from rounding the final spot-price product down. [Calculation](src/FeastHook.sol:529)

Concrete construction: coin is currency0; `sqrtPriceX96 = 3 × 2^95`; active liquidity is `1e20`; the oracle agrees; custody and allowance permit a fill; the trader sells **two raw coin units**.

- The hook fills one unit and pays `floor(floor(1 × 1.5) × 1.5) = 1` quote unit.
- Correct rounded spot is `floor(1 × 2.25) = 2`.
- The remaining one-unit pool input is entirely consumed by LP-fee rounding.
- Without the fill, the two-unit input yields two quote units under the venue’s integer arithmetic.

The fill therefore reduces proceeds from two units to one. A router requiring the otherwise achievable two-unit minimum reverts. This contradicts the plan’s spot-payment promise and the census’s “never less than the curve” claim. [Plan](plans/v16/plan.md:85), [census](docs/site-census.md:198)

The pricing witness copies the same double-floor expression, so its equality assertion cannot detect this discrepancy. [Copied calculation](test/FeastInternalFill.t.sol:65)

**Root-cause scope:** The inverse helper and converter use the same arithmetic pattern. This finding counts the new use as an actual seller payment; it does not recount the converter’s pre-existing execution-bound residue. [Inverse](src/FeastHook.sol:540), [converter](src/FeastConverter.sol:280)

**Fix and second-order check:** Preserve precision until final rounding and test against an independent rational-price calculation in both currency orderings. Simply squaring `sqrtPriceX96` in `uint256` introduces overflow at valid high prices; retain overflow-safe arithmetic and recheck allowance/custody bounds after conversion.

**L3 — The “never touches the quote token” witness does not test that property.**

`test_aFillNeverTouchesTheQuoteToken` uses an ordinary transferable quote, asserts a fill occurred, and checks only that the hook’s final quote balance is zero. It neither freezes the quote nor observes calls to it. A withdrawal and redeposit during the fill could preserve that final balance while introducing a token-controlled swap refusal. [Entire witness](test/FeastInternalFill.t.sol:345)

**Fix and second-order check:** Exercise an actual fill against a frozen quote, with the router receiving quote claims so its own payout does not require a token transfer. Require successful settlement and a nonzero `InternalFill`. This is a test correction; it introduces no production behavior change.
